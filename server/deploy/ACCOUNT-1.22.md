# ChatQ 1.22 account deployment

1. Build `server` before the admin UI so its exported router types exist. Keep all tRPC packages at 11.9.0. Build the Android app with the existing signing key; do not uninstall an existing user app to upgrade it.
2. Back up PostgreSQL with `pg_dump -Fc` to the approved data volume, outside the web root. Apply `migrate-1.22.sql` using `psql -v ON_ERROR_STOP=1`. It only adds three user columns and a unique index. Keep the dump private and retain the prior API image and Compose configuration.
3. Start only the API service with `compose.input.yaml` as an override. The ChatQ runtime sets `CHATQ_DISABLE_APPLE_WEBHOOK=true`; legacy mock Apple verification/restore is also blocked for the `chatq` app configuration. This does not implement a real Apple billing integration. Jeepay remains disabled until merchant configuration and actual payment/refund acceptance are complete.
4. Terminate public HTTPS at Caddy and expose the API on loopback only. The account router requires the proxy's `X-Forwarded-Proto: https` in production. Preserve trusted proxy headers and do not expose port 13000 publicly. Restrict CORS to the project's actual origins.
5. The deployed domain is `lt.youling.lol`. The project's Caddyfile is imported by the host's main Caddyfile. The host also sets `default_sni 103.149.91.78` globally for IP TLS clients that omit SNI; do not add a second global options block when importing the project snippet. IP certificates use the short-lived ACME profile and automatic Caddy renewal. See the [Caddy TLS directive](https://caddyserver.com/docs/caddyfile/directives/tls) and [global options](https://caddyserver.com/docs/caddyfile/options).
6. Verify HTTPS health, HTTP account REST status 426, unauthenticated status 401, mock Apple callback rejection, immutable asset hashes, and unchanged existing billing/user data before changing the Android latest-version pointer. Keep the prior assets and APKs.

Accounts use usernames, passwords and an explicit one-time recovery code. Sessions expire after 30 days; password change, recovery and logout revoke earlier token versions. Guest registration upgrades the current user ID and retains its subscription and usage. Signing into an existing account does not merge a different guest's entitlements. Local chats/personas/favorites stay local; use the existing encrypted backup/sync features for records. No SMS or email verification delivery is configured by this release.

To roll back the API, restore the prior Compose override and recreate only the API service. Additive columns can stay in place; do not drop them or restore an older database over newer user activity. Restore the old admin index if needed, keeping both sets of hashed assets. Database recovery requires a separate reviewed decision using the private dump.
